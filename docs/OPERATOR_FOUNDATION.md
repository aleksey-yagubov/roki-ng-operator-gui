# Основа операторского приложения

Состояние на 2026-09-26. Основной запуск: `python roki_operator.py`.
Основной поток direct-gst реализован, OSD отложен. При старте не импортируются
GI/GStreamer; они загружаются при запросе видео. Видеоприёмник не требует
NumPy или OpenCV; NumPy используется локальным LAB-предпросмотром.
Docking проверяется на основном интерфейсе: `scripts/test_operator_gui.py`.

## Обязательные правила

- Адрес робота задаётся явно. Нет discovery, broadcast и подключения при старте.
- `--robot` заполняет поле адреса, но не устанавливает соединение.
- Подключение выполняет hello/welcome, heartbeat, подписку на журнал
  и `body.power` (1 Гц) для напряжения аккумулятора.
  Оно не захватывает управление, не меняет режим, не запускает камеру,
  не запрашивает автоматически каталоги или параметры.
- Списки слотов, тестов и ключей параметров загружаются отдельными кнопками.
  Открытие, перенос, закрытие или восстановление панели не является командой роботу.
- Разрыв связи с оператором не должен останавливать автономную игру.
  Правило относится к роботному supervisor, не только к интерфейсу.
- Потеря оператора при ручном управлении должна прекращать ручной drive
  по watchdog. Это другой случай, не основание останавливать автономный футбол.
- После восстановления связи нельзя автоматически воспроизводить старые команды,
  возобновлять ручную ходьбу или повторно запускать тест.

## Что уже работает

Панели KDDockWidgets: подключение, управление, состояние, слоты/тесты, параметры,
источники данных, журнал, диагностика, настройки видео и изображение QImage.
Панели перемещаются, объединяются во вкладки и выносятся
в отдельные окна. Закрытая панель снова открывается через меню «Панели».
Сохранение/восстановление раскладки явное, кнопками. Используется стандартный
стиль Qt Controls, без собственной темы и рисованных кнопок.
Минимальный размер главного окна 800x700: ниже этого размера текущая docking-
раскладка обрезалась. Нативное ограничение окна не позволяет пользователю
ужать её до такого состояния; длинное содержимое панелей прокручивается.

Сверху постоянно видны связь, идентификатор робота и режим. Нижняя строка
показывает наблюдение/отсутствие актуальной связи, напряжение аккумулятора и RTT.
`body.power.data.voltage_v` показывается в вольтах, без пересчёта ADC и без
выдуманного процента заряда. Учитываются `valid`, `age_ms` и время после получения
на ПК: через 3 с данные устарели. Отсутствующие/ошибочные данные не становятся 0 В,
симуляция помечается отдельно. Подсказка показывает ADC, возраст и ошибку.
Та же индикация есть в панели состояния. Worker status является снимком: рядом показан его возраст,
при отключении интерфейс предупреждает об устаревших данных.

Каталоги приходят с робота. Клиент не знает заранее число слотов, обходит
страницы по `next_offset`. По кнопке запроса тестов запрашиваются их описания,
затем строятся карточки с полями и отдельными кнопками запуска.
Поле `when: custom` отображается/передаётся только для custom-режима.
Недоступный режим теста нельзя запустить, причина показывается в карточке.
Для выбранного параметра запрашиваются значение и метаданные отдельными
`params.get` и `params.describe`.

Редактор параметра показывает тип, пределы, описание и момент применения.
Ключи фильтруются по группе (первый компонент имени: motion, vision и т.д.)
и подстроке. Группы берутся из каталога робота, не зашиты в клиент.
Редактор появляется только после выбора ключа; высота определяется содержимым
с ограничением 60% панели и прокруткой. Остальное пространство занимает список.
Запись выполняется отдельной кнопкой с проверкой типа/диапазона; сервер также
проверяет значение и сохраняет его. Черновик не сбрасывается по heartbeat.
Исходные ответы скрыты под галочками, это не основной вид интерфейса.

## Ручное управление

Явные шаги: получить lease, включить MANUAL, вызвать нужное действие.
Получение/освобождение lease находится в верхней панели и доступно независимо
от открытой вкладки. Для изменения параметров переключаться в MANUAL не нужно.
В панели тестов и слотов явно показана причина блокировки запуска: нет связи,
нет управления, другой режим, ожидаемый ответ, выполняемое движение либо
неизвестный исход команды. Там же есть кнопка перехода в MANUAL; переход
никогда не выполняется автоматически.
Walk / Actions / Head повторяют уникальную часть старой раскладки
`tools/roki_manual_qt.qml`, без дублирования подключения, журнала и слотов.
Hard L/R остаются неактивными: аппаратный удар пока отсутствует в новом API.
Диапазон tilt берётся из нового контракта (-2600..950), не старого +/-2500.

WASD посылает drive 20 раз/с только при удержании. Отпускание отправляет три
нулевых sample без ACK. Q/E и Shift+WASD выполняют разовый прыжок.
Стрелки головы: вверх увеличивает tilt, вниз уменьшает; влево увеличивает pan.
Экранные кнопки вызывают тот же nudgeHead, что и клавиатура.
Клавиатура включается явно по галочке и действует на всё приложение.
Потеря активности приложения или скрытие ручной панели освобождает клавиши.
Просроченные более 150 мс drive updates от GUI сетевой поток отбрасывает;
во время зависания GUI свежая ходьба не синтезируется сетевым потоком.

Разовые движения не накапливаются: кнопки блокируются до ответа и завершения job.
Статус активного job опрашивается раз в 500 мс для компенсации потерянных событий.
Плавный stop и жёсткий сброс доступны также в верхней панели.
Сброс снимает ожидающие запросы/повторы перед отправкой barrier, чтобы старое
движение не ушло после остановки. Это сброс host/STM queue, не отключение питания
и не гарантия остановки уже исполняемой интерполяции серв.
При неизвестном исходе команды (таймаут ответа) новое движение блокируется
до явного сброса очереди или закрытия сессии.

Обработка игры, редактор серв и OSD пока не подключены.
Основное видео описано в [VIDEO_RECEIVER.md](VIDEO_RECEIVER.md).
Две ошибки Wayland docking исправлены локальным патчем, см.
[WAYLAND_DOCKING.md](WAYLAND_DOCKING.md).

## Потоки и ограничения памяти

Панель «Источники данных» получает каталог через явный `data.list`.
Выбор источника не отправляет запрос: кнопка «Снимок» вызывает `data.snapshot`,
«Подписаться» включает `data.subscribe` с выбранной частотой, «Отписаться»
вызывает `data.unsubscribe`. Для чтения lease и MANUAL не требуются.
Источники включают system.workers, motion.state, camera.state, detection.state, body.power.
Это наблюдение за состоянием, не запуск камеры, детектора или движения.

Данные показываются как поля со значениями; вложенные имена разворачиваются
в пути. Исходный ответ скрыт под галочкой. Видны доступность источника,
сообщённый роботом возраст данных, время с получения на ПК и пропуски sample.
Часы робота и ПК не сравниваются. Смена выбранного источника сохраняет явно
запрошенные подписки; отключать их нужно кнопкой. Разрыв соединения сбрасывает
локальные подписки, reconnect их не возобновляет, кроме автоматической `body.power`.
Она не включает IMU и не требует lease. Её можно отключить в этой же панели;
повторное подключение включает её снова. Полученные sample не засоряют
журнал. Кеш ограничен каталогом до 64 источников, представление до 256 полей.

```text
Qt GUI thread
  QML, docking, модели, локальные фильтры, действия пользователя
       |
       | queued Qt signals
       v
operator-udp QThread
  неблокирующий UDP socket + QSocketNotifier
  MessagePack, проверка адреса/session/token/id/op, heartbeat, повторы
```

Чтение сокета пробуждается по готовности, не периодическим опросом.
Сетевой QTimer обслуживает только таймауты, heartbeat и выдачу пакетов событий.
За одно событие готовности обрабатывается максимум 32 датаграммы.

Один обычный request находится в полёте; heartbeat не ждёт его завершения.
Очередь запросов ограничена 32. Повторяется тот же пакет с тем же ID, максимум
пять отправок с интервалом 250 мс. Таймаут ответа не означает отмену операции.
UDP payload ограничен 1200 байтами согласно текущему `manual-1`; включён DF.
uint64 идентификаторы остаются Python int, не передаются в QML как JS Number.

Входная очередь событий ограничена 256 записями. В GUI одновременно находится
не более одной ожидающей обработки пачки до 32 событий; после обработки GUI
подтверждает её приём локальному сетевому потоку. Переполнение видно в журнале.
Это локальное ограничение очереди, не сетевые ACK на каждое событие.

GUI хранит максимум 2000 записей журнала, поддерживает уровень, поиск,
фильтр источника, очистку, автопрокрутку по галочке и паузу просмотра.
Пауза не прекращает получение записей; при продолжении показывается ограниченная
свежая история. Пропуски sequence и серверное вытеснение записей показываются
как предупреждения. Время в строке журнала означает получение на компьютере,
не синхронизированные часы робота. Уведомления счётчиков журнала объединяются,
вместо переоценки всей панели на каждую строку.

Рабочие потоки не дают параллельного исполнения Python CPU-bound кода при GIL.
Их задача здесь: отделить сетевой жизненный цикл от GUI и не делать blocking I/O.
Объём работы каждой очереди ограничен. Нормальные действия GUI не используют
`wait()` или `join()`. Ожидание окончания сетевого потока есть только при
финальном закрытии приложения; сам поток не выполняет блокирующее чтение.

`Ctrl+C` завершает приложение с кодом 130 через обычный обработчик SIGINT,
без отдельного таймера опроса сигнала. Обработчик не выбрасывает исключение
внутрь QML getter-а, где PySide иначе выдаёт ошибку metacall.

## Автономная игра и закрытие сессии

GUI при отключении посылает только best-effort `session.close`, прекращает
heartbeat и очищает локальную очередь запросов. При потере связи команды
остановки/смены режима не отправляются; автоматического reconnect нет.

**Ограничение текущего роботного runtime:** `manual-1` ещё не реализует GAME.
У него отзыв владельца вызывает `_release()` с переходом в IDLE и остановкой
ручной активности. При добавлении автономной игры supervisor должен отделить:

- операторскую сессию, подписки и права ручного вмешательства;
- автономную задачу игры, которая живёт без этой сессии;
- временное ручное управление, которое обязано иметь watchdog.

Тестовый сервер с состоянием GAME проверяет только то, что GUI не отправляет
останавливающих команд при отключении. Он не доказывает правильность будущей
реализации игры на роботе. Роботный репозиторий на этом этапе не изменялся.

## Диагностика будущего OSD

OSD согласован для передачи через MessagePack, отдельно от RTP-видео.
В RTP планируется только UnicamSequence. Точная RTP extension и схема OSD sample
ещё не реализованы: сначала согласуем их в `roki-ng/docs/DISPLAY_PROTOCOL.md`,
затем реализуем обе стороны без параллельного wire-протокола.

Если связанный с OSD кадр вытеснен из кеша, интерфейс обязан показать это явно:
счётчик промахов по потоку/слою, последний sequence, причина и время события.
Нужно различать «вытеснен», «ещё не пришёл», «не удалось сопоставить sequence».
Для частых промахов нужны агрегированные счётчики и ограниченные по частоте
предупреждения, не поток одинаковых строк. На чужой кадр разметку не переносить.
В панели диагностики сейчас указано, что эти показатели ещё не измеряются.

## Проверки

```sh
python -m unittest discover -s tests -v
python scripts/test_operator_gui.py
python scripts/check_runtime_compat.py --runtime-dir ../roki-ng
python scripts/check_runtime_compat.py --exercise-controls
```

Первые проверки используют только loopback. GUI-тест делает настоящие клики
QTest, проверяет каталоги, параметры, журнал, перенос панели, раскладку и окно
800x700. Снимки и результат: `artifacts/operator-gui/`.
Дополнительно подаётся всплеск 600 сообщений журнала. В выполненном запуске
максимальный интервал тестового GUI-таймера с периодом 20 мс составил 52 мс;
проверка не является универсальной гарантией задержек на другом компьютере.

Последний тест запускает настоящий supervisor в локальном `--simulate`
с `--body-disabled --skip-bootstrap`, временным state-dir и случайным UDP-портом.
Он не подключается к железу. На текущем runtime получены 57 слотов,
4 семейства тестов и 73 ключа параметров.
С `--exercise-controls` используется SimHardware (без body-disabled), проверены
lease, MANUAL, base_stand, голова, drive, stop, прыжковый тест, запись параметра
и освобождение управления. Камера не запускается.

Полноценная проверка на реальном роботе и Windows ещё не проводилась.
