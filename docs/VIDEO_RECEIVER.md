# Приём видео

Порядок работы описан в [CAMERA_STREAMS_VIEWS.md](CAMERA_STREAMS_VIEWS.md).
GUI использует только именованные H.264-видеовыходы нового `videostream.*`.
Приёмник готов до subscribe; свободный порт выделяет ОС. Ручной порт и декодер
можно выбрать отдельно. Назначение RTP на роботе берётся из адреса сессии.

## Пайплайн

`udpsrc → rtpjitterbuffer → rtph264depay → h264parse → декодер → videoconvert → appsink`

Декодер: `vah264dec` на Linux или программный `avdec_h264`.
Вывод всегда appsink → RGBA → QImage с учётом stride; OpenCV/NumPy не нужны.
Инициализация GStreamer и обработка пайплайна выполняются вне GUI-потока.
Поток управления UDP независим от видео.

Один выход имеет один Receiver и последний QImage независимо от числа просмотров.
Кадры выдаёт QQuickImageProvider; не используется Python paint() в render-thread.
Хранятся только последний кадр и одно ожидающее уведомление GUI.
Вынос просмотра в другое окно и возврат не перезапускают приёмник.
Смена run_id/SSRC очищает кадр и требует явного повторного подключения.

## Измерение FPS

Примерно каждые 0,5 секунды вычисляется прирост штатного GstBaseSink-счётчика
`stats.rendered`, делённый на прошедшее монотонное время. Это скорость поступления
кадров в sink, не перерисовки Qt. При остановке кадров FPS падает до нуля.
Заданный FPS сенсора не подставляется вместо измеренного; fpsdisplaysink не нужен.

## Проверки

`python scripts/test_video_gui.py` запускает локальный videotestsrc → H.264 RTP,
проверяет VA/программный декодер, 800×650, FPS, несколько просмотров и docking.
`python scripts/check_gstreamer.py` проверяет RTP → QImage без графического окна.
Результаты GUI-теста и снимки: `artifacts/video-gui/`.

Windows и аппаратный отправщик робота требуют отдельной проверки.
Показания FPS не гарантируют отсутствие потерь UDP или показ каждого кадра.
