# Проверка удержания GPU-буферов

Дата: 2026-09-26. Ноутбук с Intel UHD Graphics 620 (Kaby Lake-R, i915),
Linux/Wayland, GStreamer 1.28.7. Это измерения конкретного стека, не гарантия
для других драйверов, декодеров или Windows.

## Методика

Скрипт: `scripts/probe_gpu_retention.py`. Ничего не устанавливает и не
подключается к роботу. Нужны GI для Gst/GstVideo и установленные плагины
VA, OpenGL, app, videotestsrc, h264parse, fakevideosink.

```sh
python scripts/probe_gpu_retention.py
```

Источник: движущийся тестовый шар, 800x650, 60 кадров/с. Для проверки декодера
локальный `vah264enc` формирует H.264, затем `vah264dec` его декодирует.
В тестах `vpp-*` кодеков нет, только `vapostproc disable-passthrough=true`.

После проверяемого элемента стоит `tee` с двумя ветками:

- Маленькая leaky-очередь и `fakevideosink`: счётчик кадров живого потока.
- Маленькая очередь и `appsink`: Python хранит ссылки на `GstSample` в
  ограниченном `deque`, не отображает GPU-память в CPU и не копирует пиксели.

Сначала 2 секунды без истории, затем 6 секунд с историей последних 120 кадров,
затем история очищается и поток работает ещё 2 секунды. Отдельно закреплён
один старый кадр, как у диагностического окна, которое давно не обновлялось.
Таким образом, удерживается до 121 различного кадра, не считая внутренних
буферов пайплайна. В истории проверены 120 разных буферов и memory handles.

`appsink` объявляет поддержку `GstVideoMeta` через `propose-allocation`.
Это необходимо для корректного согласования DMA-BUF с его stride/modifier.
Обычный `fakesink` без поддержки этой метаинформации дал `not-negotiated`;
его заменили на подходящий для такого теста `fakevideosink`.

GPU-память измеряется по `/proc/self/fdinfo/*`, полю `drm-total-system0`,
с дедупликацией файловых дескрипторов одного DRM-клиента. RSS записывается
отдельно: RSS процесса не отражает весь объём удерживаемых GPU-ресурсов.

## Результаты для 120 кадров

Все семь окончательных тестов завершились успешно, без сообщений ERROR/WARNING.
Живая ветка продолжала работать около 60 кадров/с, как и приёмник истории.

| Источник сохраняемых буферов | FPS при удержании | Прирост GPU-памяти относительно прогретого пайплайна |
| --- | ---: | ---: |
| `vapostproc`, NV12 VAMemory | 60,01 | 104 МиБ |
| `vapostproc`, NV12 DMA-BUF | 60,02 | 105 МиБ |
| `vah264dec`, NV12 VAMemory | 60,00 | 98 МиБ |
| `vah264dec`, NV12 DMA-BUF | 60,01 | 100 МиБ |
| `vah264dec ! vapostproc`, NV12 VAMemory | 60,00 | 105 МиБ |
| `vah264dec ! glupload`, GL external-oes | 60,02 | Около 100 МиБ общей VA/GL памяти |
| `vah264dec ! glupload ! glcolorconvert`, GL RGBA 2D | 60,07 | 720 МиБ у GL-клиента |

У прямого GL-импорта одни DMA-BUF учитываются у двух DRM-клиентов как shared.
Их нельзя просто сложить и объявить расходом в 200 МиБ.

720 МиБ последней строки включают реальные выделения GL/драйвера в этом
пайплайне, а не только номинальный размер RGBA-пикселей. Причина такого
дополнительного расхода здесь не установлена. Нельзя переносить это число
на любой GL-драйвер или считать, что RGBA всегда занимает столько памяти.

Максимальный интервал между полученными кадрами в фазе удержания был
примерно 18-25 мс. Это не измерение задержки вывода на экран. После заполнения
истории GPU-память стабилизировалась: замеры после 240 принятых кадров и в конце
фазы практически одинаковы. Это короткий тест, не длительный поиск утечек.

После освобождения ссылок объём выделенной GPU-памяти остался примерно тем же.
Освобождение кадра возвращает его в пул, а не обязательно освобождает память
драйвера. Очистка истории сама по себе не обещает немедленного уменьшения
занятой памяти. Поток после очистки продолжал идти с 60 кадрами/с.

## Дополнительная проверка 240 кадров

```sh
python scripts/probe_gpu_retention.py --case decode-dmabuf --capacity 240 --seconds 12 --output artifacts/gpu-retention-240
```

Сохранялись последние 240 кадров (4 секунды видео) и один закреплённый старый
кадр. За фазу удержания приняты 721 кадр, живая ветка тоже получила 721 кадр.
Скорость 60,01 кадров/с, максимальный интервал 25 мс, ошибок и предупреждений нет.
Выделенная GPU-память выросла с 29,45 до 235,54 МиБ, то есть примерно на 206 МиБ.
Замеры после 480 кадров и в конце фазы одинаковы: история ограничена, память
не продолжает расти с каждым следующим кадром в этом тесте.

## Проверка пяти секунд истории при 60 fps

```sh
timeout 55s python scripts/probe_gpu_retention.py --case decode-dmabuf --capacity 300 --seconds 30 --output artifacts/gpu-retention-300
```

Разрешение 800x650, NV12 DMA-BUF непосредственно после `vah264dec`. История
содержала 300 различных буферов (5 секунд видео при 60 fps); дополнительно,
как в предыдущих тестах, закреплён один старый кадр вне скользящей истории.

За 30 секунд фазы удержания получен 1801 кадр, живая ветка получила столько же.
Средняя скорость 60,00 кадров/с, максимальный интервал между получениями
25,6 мс. Ошибок и предупреждений нет. После очистки истории поток продолжился.

Выделенная GPU-память DRM-клиента выросла с 29,45 до 288,49 МиБ, прирост
259,04 МиБ. Это память всего тестового VA-пайплайна, включая кодирование и
декодирование; прирост измерен относительно того же прогретого пайплайна
без истории. На 600-м принятом кадре (примерно 10-я секунда удержания)
и в конце 30 секунд объём одинаковый: 295416 КиБ. После очистки истории
выделенная память пула также осталась на этом уровне.

Полные измерения: `artifacts/gpu-retention-300/decode-dmabuf.json`.

## GL-импорт и отдельная текстура

У `glupload` согласовался `RGBA, texture-target=external-oes`. В выходном
буфере присутствует `GstParentBufferMeta`: он удерживает исходный DMA-BUF.
Растёт память VA-клиента. Таким образом, GL-обёртка не отделяет историю от
поверхностей декодера и не решает проблему ограниченного пула автоматически.

В варианте с `glcolorconvert` выход принудительно задан как:

```text
glupload ! glcolorconvert ! video/x-raw(memory:GLMemory),format=RGBA,texture-target=2D
```

Вход конвертера фактически external-oes, выход 2D. В выходных буферах нет
`GstParentBufferMeta`, память VA-клиента остаётся постоянной, растёт GL-память.
Здесь история действительно отделена от исходных поверхностей, но ценой
GPU-обработки и существенно большего расхода памяти в измеренном варианте.

## Вывод для архитектуры

На этом ноутбуке хранить ссылки на NV12 VA/DMA-BUF кадры непосредственно после
декодера можно: пул расширяется, удержание до 300 кадров не остановило декодирование
в выполненных тестах.
Обязательный перевод всей истории в RGBA перед кешированием не оправдан этим
тестом. Предпочтителен общий ограниченный кеш NV12 и импорт нужных кадров для
отображения. Лимит кеша нужен по числу кадров, времени и бюджету памяти,
с учётом отдельно закреплённых кадров диагностических панелей.

Тест не проверяет `qml6glsink`, смену окон, поиск по UnicamSequence,
синхронизацию с OSD, корректность пикселей при повторном отображении,
неограниченное хранение или Windows/D3D11. У декодера с ограниченным пулом
ситуация может отличаться. Общий вывод "VA-буферы нельзя удерживать" неверен,
но противоположное утверждение "любое количество всегда безопасно" тоже.

Исходные результаты, caps, allocation types и снимки памяти:
`artifacts/gpu-retention/*.json`, логи: `*.log`, итог: `suite.json`.
