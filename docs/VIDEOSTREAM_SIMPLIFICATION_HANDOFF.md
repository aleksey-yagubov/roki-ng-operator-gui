# Основному агенту roki-ng: упрощение видеостримов

Статус: реализовано в runtime и GUI 02.10.2026. Ниже сохранено исходное предложение.
Итоговый контракт: `roki-ng/docs/GUI_CAMERA_VIDEOSTREAM_HANDOFF.md`;
текущий интерфейс: [CAMERA_STREAMS_VIEWS.md](CAMERA_STREAMS_VIEWS.md).
В итоговой реализации только H.264, поддержки JPEG больше нет.
Это заметка для изменения основного контракта, не отдельный wire-протокол GUI.
Точные команды, схемы и примеры сначала зафиксировать в документации roki-ng,
затем передать обновлённый handoff агенту GUI.

## Что меняем

Текущая схема слишком буквально выставляет оператору жизненный цикл объектов:
create -> start -> attach -> просмотр -> detach -> stop -> destroy.
Произвольное количество определений с UUID не нужно.

- Каталог содержит только видеовыходы, действительно поддерживаемые воркерами.
- Имя видеовыхода соответствует имени воркера. Предлагаемое соответствие:
  `stream` — прямой захват direct-gst; `camera` — кадры camera-worker;
  `localisation` — диагностическое изображение локализации.
- Новые пункты добавляются по факту реализации выхода в воркере, не заранее.
- На один воркер приходится один именованный видеовыход, одна конфигурация
  кодирования и не более одного запущенного пайплайна этого выхода.
- Не нужны пользовательские create/destroy и случайный stream_id для выбора.
  Повторный запуск уже работающего выхода не создаёт второй пайплайн.
- Один кодер и RTP-пакетизатор обслуживают всех получателей через multiudpsink.
  Несколько получателей не означают несколько захватов или кодеров.

Это не требует переносить кодирование в каждого производителя: stream-worker
может по-прежнему владеть GStreamer. Имя идентифицирует видеовыход, а не процесс,
в котором расположен кодер. Ограничения камеры и аппаратных кодеров сохраняются:
конфликт ресурсов сообщается явно, без скрытого переключения/остановки источников.

## Жизненный цикл и права

- Оператор явно запрашивает каталог и выбирает источник. Подключение к роботу
  само по себе не запрашивает видео и не запускает производителей.
- Настройки общие для именованного выхода, не отдельные для каждого получателя.
- Основной сценарий GUI: источник -> настройки -> «Смотреть» / «Отключиться».
  Локальный UDP-приёмник готовится до запроса отправки кадров роботом.
- Если выход уже работает, новый получатель присоединяется к нему без рестарта.
  Нельзя незаметно применить его настройки поверх настроек текущих получателей.
- Запуск и изменение общей конфигурации требуют управления. Наблюдатель может
  присоединиться к уже работающему выходу и отключить только свой приём.
- Подписка относится к сессии оператора; целевой IP берётся из этой сессии,
  UDP-порт задаётся получателем. Повторный запрос не дублирует получателя.
- Последний получатель ушёл или потерял сессию: кодирование/передача прекращаются.
  Для direct-gst прекращается также его собственный захват камеры.
- Явная остановка для всех требует управления. Повторная остановка безопасна;
  опрос статуса и прежние подписки не должны сами снова запускать выход.
- Изменение геометрии/кодека работающего выхода, если нужен рестарт, выполняется
  явно и с предупреждением о влиянии на всех получателей.
- Отключение оператора не останавливает автономную игру или необходимые ей
  camera/detection/localisation/neural-компоненты.

Сохранить обработку повторных UDP-запросов и неизвестного исхода команды.
Внутренний run_id/SSRC можно оставить для обнаружения рестарта и очистки старого
приёма; это не пользовательский идентификатор создаваемого объекта.

## Производство кадров только по запросу

- Без запроса на диагностический видеовыход производитель не рисует разметку,
  не собирает preview, не копирует и не публикует его кадры в IPC.
- При появлении первого получателя stream-worker через существующее управление
  воркерами включает нужный выход; после последнего получателя выключает его.
- Учёт потребности централизован: отключение одного получателя не выключает
  выход для остальных. Ошибка запуска и рестарт/падение stream-worker не должны
  оставлять производителя бесконечно генерировать никому не нужный preview.
- Эти требования относятся к дополнительному видео для просмотра. Рабочие
  кадры, нужные алгоритмам, продолжают публиковаться по их потребности.
  Например, отсутствие оператора не отключает кадры camera-worker для детектора.
- Для camera-выхода использовать имеющиеся рабочие кадры; не запускать второй
  захват ради просмотра. Для direct-gst без получателей собственный захват не нужен.

## Что требуется клиенту

Каталог: постоянное имя, понятное описание, поддерживаемые настройки, доступность
и причина недоступности. Статус: состояние выхода, применённые настройки, число
получателей, подключён ли текущий оператор, параметры RTP и причина ошибки.

Панели «Камера», «Стримы» и «Просмотры» остаются раздельными:

- «Камера» управляет camera-worker и ISP, не прямым захватом GStreamer.
- «Стримы» выбирает выход воркера, настраивает и включает приём. Поля direct-gst
  показываются только для соответствующего выхода stream-worker.
- «Просмотр» — локальная панель QImage. Таких панелей может быть много;
  один принимаемый выход использует один UDP-приёмник и один декодер на ПК.
  Открытие ещё одного просмотра не создаёт подписку. Закрытие панели только
  скрывает её; отключение приёма является отдельным явным действием.

OSD и datastream остаются отдельными механизмами. Эта переработка их не заменяет.

## Переход и проверки

Сохранить работающее кодирование, multiudpsink и учёт сессий; упростить модель
ресурсов и управление, а не переписывать весь медиатракт. Несовместимое изменение
команд обозначить версией/capability: старый GUI не должен молча ошибаться.
Уточнить в handoff соответствие старых runtime/direct-gst новым именам воркеров.

Проверить: повторный запуск не создаёт копии; два получателя делят один пайплайн;
уход одного не влияет на другого; уход последнего снимает запрос preview;
обрыв сессии и ошибка кодера освобождают ресурсы; игра без оператора продолжается;
наблюдатель не меняет общие настройки; конфликт камеры не останавливает её скрытно.

Геометрию 800x650 не заменять автоматически на 800x648. Сейчас ограничение
кратности 8 относится к RTP/JPEG; H.264 по умолчанию оставляет 800x650.
